# AWSインフラ設計(Well-Architected Framework準拠)

> 親ドキュメント: [concept.md](concept.md)
> 構成: フロントエンド Next.js(別ホスティング) / バックエンド Ruby on Rails(APIモード) / インフラ AWS

---

## 0. 前提とスコープ

**これは本番運用設計ではなく、ハッカソン期間限定のデモ環境設計。**
ただし「とりあえず動けばいい」で終わらせず、AWS Well-Architected Frameworkの5本柱それぞれについて
**意図的にどう判断したか**を記録する。フレームワークが求めているのは全項目の無条件最大化ではなく、
**トレードオフを自覚して選んでいるかどうか**。ここがドキュメント化の本体。

前提条件:

- チームはAWS未経験。VPC・ECS・ALBを手で組む学習コストは避ける
- デモ公開期間は数日〜1週間程度。24/365の可用性は要求されない
- 決済情報、メール、パスワードは扱わない。冷笑図鑑では顔写真を保存するため、非公開オブジェクトストレージと削除方針を必須とする
- 審査員・観客に見せられれば成功。過剰設計は時間の無駄

## 1. 全体構成

```
                    ┌─────────────────────────┐
観客/審査員 ──HTTPS──▶│  Next.js (フロントエンド)  │
                    │  Amplify Hosting        │
                    └────────────┬─────────────┘
                                 │ HTTPS (CORS)
                                 ▼
                    ┌─────────────────────────┐
                    │  Rails API (App Runner)  │
                    │  ・LLM呼び出し(Claude)    │
                    │  ・スコア確定・DB書き込み   │
                    │  ・講評文/称号生成         │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────┴─────────────┐
                    ▼                           ▼
        ┌───────────────────┐      ┌──────────────────────┐
        │  RDS (PostgreSQL)  │      │  Anthropic API         │
        │  スコア履歴・ランキング │      │  (AWS外・直接HTTPS)    │
        └───────────────────┘      └──────────────────────┘
```

**リアルタイム加点(辞書+kuromoji.js)はブラウザ内で完結し、Railsを一切経由しない。**
Railsが呼ばれるのは「発話が終わった後」の低速経路(LLM講評・確定スコア保存)のみ。
これにより、AWS側の設計はリアルタイム性を気にしなくてよくなる — 数秒のレイテンシは許容範囲。

## 2. 5本柱ごとの設計判断

### 2.1 運用上の優秀性(Operational Excellence)

| 判断 | 採用する仕組み | 理由 |
|---|---|---|
| デプロイ方式 | **App Runner** のソースコードデプロイ(GitHub連携) | `git push`するだけで自動ビルド・デプロイ。ECS Fargateのようなタスク定義・ALB設定が不要 |
| 監視 | **CloudWatch Logs**(App Runner標準搭載) | 追加設定なしでログが自動収集される。ハッカソン中はこれで十分、ダッシュボード構築は不要 |
| 構成管理 | Rails側の設定は環境変数化し、App Runnerの「ランタイム環境変数」機能で注入 | Infrastructure as Codeまではやらない(Terraform/CDKは温存ネタ扱い。§4参照) |
| ロールバック | App Runnerはデプロイ履歴から1クリックで前バージョンに戻せる | 壊れたデプロイをデモ直前に戻す手段を確保しておく |

> **意図的にやらないこと**: Terraform/CDKによるコード化、Blue/Greenデプロイ、カナリアリリース。
> ハッカソンの規模でこれらを導入するコストは、得られる運用上の優秀性の向上を上回る。

### 2.2 セキュリティ(Security)

| 判断 | 採用する仕組み | 理由・トレードオフ |
|---|---|---|
| 通信の暗号化 | App Runnerは自動でHTTPS化される(ACM証明書の手動設定不要) | 標準機能なのでタダで得られる。ここはケチる理由がない |
| シークレット管理 | Anthropic APIキー・DBパスワードは **SSM Parameter Store**(SecureString)に保存し、App Runnerの環境変数として注入 | Secrets Managerより安価(Parameter Storeは無料枠内で収まる規模)。コードやリポジトリに直書きしない |
| DBへのアクセス経路 | **RDSをパブリックアクセス可にし、セキュリティグループで絞る**(VPCコネクタ+NAT Gatewayは使わない) | 下記「検討した代替案」参照。意図的に選んだ簡易構成 |
| IAMロール | App Runnerのインスタンスロールは「CloudWatch Logs書き込み」「SSM Parameter Store読み取り」の最小権限のみ | 管理者権限系のマネージドポリシーは使わない |
| 個人情報 | 実名・連絡先・パスワードは収集しない。冷笑図鑑の顔写真は非公開バケットに保存し、DBにはActive Storageの参照と撮影時刻だけを持つ | 顔写真を公開URLやDBバイナリとして保持せず、閲覧権限と削除をAPI側で制御できるようにする |

**検討した代替案: RDSへのアクセス経路**

| 案 | メリット | デメリット |
|---|---|---|
| **A: パブリックアクセス+SG絞り込み(採用)** | VPC設定不要、AWS初心者でも詰まらない | セキュリティグループの設定を誤ると全世界に開放されるリスク |
| B: VPCコネクタでプライベート接続 | 本来あるべき姿に近い | App Runnerからの全アウトバウンド通信がVPC経由になり、Claude APIへの外部通信にも**NAT Gateway`が必須になる**(月額$30〜+データ転送量課金) → 「最低限」の方針と矛盾する上に、VPC/サブネット/ルートテーブルの理解が必要になり初心者には重い |

→ **Aを採用**。理由: ①ハッカソンの短期間デモ環境であること、②機密情報を扱わないこと、③DBパスワードを強力なランダム値にし終了後ローテーション/削除すること、の3点でリスクを許容範囲と判断。本番移行時は迷わずBに切り替える。

### 2.3 信頼性(Reliability)

| 判断 | 採用する仕組み | 理由 |
|---|---|---|
| ヘルスチェック・自動復旧 | App Runner標準機能(追加設定不要) | 落ちたら自動で再起動してくれる。手動監視は不要 |
| DBバックアップ | RDSのデフォルト自動バックアップ(7日保持)を維持する | 無料枠内。無効化するメリットがない |
| マルチAZ | **使わない(シングルAZ)** | Multi-AZは冗長化のためコストがほぼ2倍。デモ環境で数時間のダウンタイムが命取りになるわけではないので、コストに見合わないと判断 |
| リージョン | 単一リージョン(ap-northeast-1) | マルチリージョンは明らかにオーバーキル |

> **意図的に許容するリスク**: RDSインスタンスが単一障害点になる。デモ直前に軽く動作確認すること、
> 本番運用に持ち越すならMulti-AZ化を検討することをTODOとして残す。

### 2.4 パフォーマンス効率(Performance Efficiency)

| 判断 | 採用する仕組み | 理由 |
|---|---|---|
| Railsのスケーリング | App Runnerのオートスケール(最小1〜最大3インスタンス程度) | 想定同時アクセスは審査員+観客の数十人規模。過剰なキャパシティ確保は無駄 |
| DBインスタンスサイズ | `db.t4g.micro`(Graviton, バーストパフォーマンス型) | 無料利用枠対象になりうるサイズ。読み書き量が少ないワークロードに適合 |
| キャッシュ層 | **導入しない**(ElastiCache等) | リアルタイム性が必要な処理はそもそもブラウザ内で完結しているため、サーバー側にキャッシュを置く動機がない。時間が余れば温存ネタとして検討 |

### 2.5 コスト最適化(Cost Optimization)

| 判断 | 採用する仕組み | 理由 |
|---|---|---|
| NAT Gateway | **使わない** | 前述の通り、VPCコネクタを避けることで月$30〜の固定費を丸ごと削減 |
| RDSインスタンス | `db.t4g.micro`(無料利用枠の対象になりうる) | 新規アカウントなら実質無料〜低額に収まる |
| App Runner | 使用量課金(常時起動よりは安いが、最小インスタンス数分の待機コストは発生する) | ECS Fargate+ALBの構成より管理コスト・固定費ともに低い |
| 後片付け | ハッカソン終了後は **RDS・App Runnerサービスを削除する**(§6のチェックリスト参照) | 放置すると多くはないが確実に課金され続ける。デモ終了=即削除をルーティン化する |

## 3. 技術スタック確定表

| レイヤー | 選択 | 備考 |
|---|---|---|
| フロントエンド | Next.js | 既に確定。App Runnerではなく別ホスティング(Amplify Hosting等)を想定 |
| バックエンド | Ruby on Rails(APIモード、`rails new --api`) | Next.jsからCORS経由で直接叩く。SSR用のNext.js APIルートは介さない |
| バックエンドホスティング | AWS App Runner | ECS Fargateより設定項目が少ない。ソースコード連携で自動デプロイ |
| DB | Amazon RDS for PostgreSQL(`db.t4g.micro`, シングルAZ) | スコア履歴・ランキング用 |
| 画像ストレージ | Amazon S3またはS3互換ストレージ(非公開) | Active Storageで冷笑写真を保存。ローカル開発時はDiskを使用 |
| 非同期ジョブ | 導入する場合は **Solid Queue**(Rails標準、DB上で完結) | LLM呼び出しは同期呼び出しで足りる規模(数秒の待ちはデモ演出として許容範囲)。Sidekiq+ElastiCache Redisは不要と判断し、インフラ要素を1つ削減 |
| シークレット管理 | AWS Systems Manager Parameter Store(SecureString) | Secrets Managerより安価 |
| LLM | Anthropic API(直接呼び出し、Bedrock経由にしない) | Bedrockのモデルアクセス申請はAWS初心者に不要な詰まりポイントになるため回避 |
| ログ・監視 | CloudWatch Logs(App Runner標準) | 追加構築不要 |

## 4. 見送った選択肢(比較検討の記録)

| 案 | 見送った理由 |
|---|---|
| ECS Fargate | VPC/ALB/タスク定義の設定が必要で、AWS初心者には学習コストが高い。App Runnerで同等の目的を達成できる |
| Terraform / CDK によるIaC化 | ハッカソンの短期間では手動構築で十分。コード化のオーバーヘッドが上回る |
| Sidekiq + ElastiCache Redis | Solid Queue(DB上で完結)で代替可能。Redisというインフラ要素を1つ丸ごと削減できる |
| VPCコネクタ + NAT Gateway | 月$30〜の固定費増加、かつVPC/サブネットの理解が必要。パブリックRDS+SG絞り込みで代替 |
| Multi-AZ RDS | コストがほぼ倍。デモ環境の許容リスクとして見送り |
| CloudFront / ElastiCacheによるキャッシュ | リアルタイム処理はブラウザ内で完結させる設計のため、サーバー側キャッシュの効果が薄い |

## 5. 作業の進め方 / チェックリスト

- [ ] AWSアカウント作成、請求アラート設定(予算超過の早期検知)
- [ ] RDS for PostgreSQL インスタンス作成(`db.t4g.micro`, シングルAZ, パブリックアクセス可)
- [ ] RDSのセキュリティグループを、想定される接続元(App RunnerのIPレンジ、または開発者の作業IP)に絞る
- [ ] SSM Parameter Storeに `DATABASE_URL` / `ANTHROPIC_API_KEY` を登録
- [ ] Rails APIアプリを作成(`rails new backend --api`)、Dockerfile作成
- [ ] App RunnerサービスをGitHub連携で作成、環境変数(SSM参照)を設定
- [ ] CORSをNext.jsのオリジンに限定して設定
- [ ] デプロイ後、`curl`でヘルスチェックエンドポイントの疎通確認
- [ ] Next.js側からRails APIへの呼び出しを一通り疎通確認

## 6. ハッカソン後の後片付け(コスト垂れ流し防止)

デモが終わったら早めに以下を削除する。放置すると特にRDSは止め忘れると継続課金される。

- [ ] App Runnerサービスの削除(または一時停止)
- [ ] RDSインスタンスの削除(スナップショットが不要なら「最終スナップショットを作成しない」を選択)
- [ ] SSM Parameter Storeに登録したシークレットの削除、またはAPIキー自体のローテーション/失効
- [ ] 冷笑写真を保存したオブジェクトストレージの削除
- [ ] 請求ダッシュボードで想定外の課金が残っていないか最終確認
